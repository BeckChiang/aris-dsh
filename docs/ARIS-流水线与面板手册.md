# ARIS 流水线与面板使用手册

> 适用版本：跨机包 2.14.2；面板前端按 2026-11-19 改版描述
> 读者：在本机用 DSH 跑科研流水线的人（不是开发者）
> 范围：`Aris_Dsh` 面板、`Aris_Wiki` 面板、底层流水线逻辑、CLI 速查

---

## 1. 这套东西由哪几块组成

| 层 | 是什么 | 在哪 |
|---|---|---|
| 宿主 | 桌面版 DSH 进程。它同时开着 Web 界面和**节拍器**（每 60 秒 tick 一次，决定要不要起下一轮） | 你正在用的这个 App |
| 面板 | 两个 Web 插件：`Aris_Dsh`（写面：启停/门禁/编译/设置）、`Aris_Wiki`（读面：总览/计划/产物/文档） | 侧栏两个入口 |
| 运行器 | `bin/aris-run.mjs` + `bin/lib/aris-runner.mjs`，负责起一轮「headless DSH 子进程」 | 工作区 `<WORKSPACE>\bin` |
| 项目状态 | 每个流水线自己的 `pipeline/state.json`（阶段、待办、门禁、指令、产物登记） | 项目目录内 |
| 运行账本 | `.aris-run/runtime.json`（本轮状态、下次时间）、`costs.jsonl`（每轮费用）、`runs/<runId>/`（每轮产物） | 项目目录内 |
| 审查通道 | 邮箱协议：请求写进 `…\kimi\aris-mailbox\in\`，Kimi 桌面客户端取件作答，回复落 `out\`，再由 `--collect` 收进 `.aris/reviews/` | 同步盘 |
| 知识库 | ARIS 上游文档 + 替代矩阵 + 项目文献/笔记/检索日志的只读索引 | `.dsh/skills/aris/references/…` + 项目目录 |

一句话概括：**宿主按节拍起一轮 → 子进程读 state 做一件原子事 → 写 `runs/` → 需要时送审 → 收尾回写 state → 面板只读地把这一切显示出来。**

## 2. 一条流水线的生命周期

### 2.1 阶段（phase）
科研流程被切成 11 个阶段，阶段 id 形如 `S4a_match`：

```
S0_prepare   准备（仓库、环境、数据入口）
S1_formal    形式化（定义、符号、命题）
S2_data      数据管线（生成、校验、归档）
S3_baseline  基线（方法实现 + 12 格评测）
S4a_match    匹配（层级匹配核心）      ← 当前在这里
S4b_plan     规划（掩码编译、四配置消融）
S4c_unfold   展开（模板库 + DAG 调度）
S4d_bridge   桥接（IFS 编码、金标准对照）
S5_experiments 端到端实验（消融、迁移、显著性）
S6_writing   写作（英文主稿、引用核验、三级审）
S7_submission 投稿（匿名稿、cover letter、预检）
```

每个阶段在 `state.json` 里是一条 `{status, todo[], done[]}`：
- `status`：`pending` / `in_progress` / `done` / `blocked_on_user`
- `todo`：还没做的条目（往往以 `S4a.1a` 这样的步骤号开头）
- `done`：已完成条目，长句中文，写清了做了什么、验证了什么

### 2.2 门禁（gate）
阶段之间不是自动推进，要过门禁。当前项目 4 个门禁：

| 门禁 | 判据 | 现在 |
|---|---|---|
| `G1_week5` | 判据覆盖率 ≥30% 且可分解率 ≥60% | 已裁：`NO_GO_FALLBACK_CONTINUE`（覆盖 20%，改叙事不改路线） |
| `G2_week11` | 基线齐、数据 5k | 已裁：`GO`（2026-11-12 15:01） |
| `G3_week16` | 4 配置单测通过且 fallback<10% | 待做 |
| `G4_bridge` | 自动 A_m ≥ 手工 A_m | 待做 |

门禁字段含义：`criteria` 判据、`status` 状态、`decision` 裁决词、`observed` 实测值、`completed` 裁决时间、`evidence` 证据文件列表。

> 通用 ARIS 项目的门禁名是 `idea_discovery` / `forensics` / `evidence_check`，判定逻辑相同。

### 2.3 一轮（wake / round）到底做了什么

每轮子进程拿到的提示词是「一段现状摘要 + 7 步固定动作」：

0. 先读提示词里注入的**现状摘要**（状态 / 当前阶段 / 阻塞 / 哪些阶段还有未完成项 / 3 条待做示例），据此判断该不该动手
1. 需要全局时读 `pipeline/PLAN-INDEX.json`（每阶段一行），再按需读 `state.json` 里相关阶段 + `pipeline/handoff/latest.md`
2. 判断：paused / blocked / done → 直接退出（`RESULT: idle`）
3. 用 `python pipeline/gate.py pipeline/state.json A` **认领 A 角色租约**（A/B 互斥，20 分钟冷却，70 分钟租约，每天 25 次唤醒上限）
4. 只做一个**原子块**（一个可验证的小目标，不做半成品）
5. 自测全绿后写 `runs/<runId>-dsh.md`（做了什么、证据、下一步）
6. 每轮**最多送审一次**（`pipeline/review/mailbox_bridge.py … send`），额度紧张时跳过
7. 收尾 `gate.py … A --finish`（若已送审加 `--async-wait`），末尾只打印一行 `RESULT: <done|idle|blocked> <一句话>`

这一轮的产物：`runs/<runId>/`（事件流、日志、提示词、meta.json）、`costs.jsonl`（一条费用）、`runtime.json`（状态与下次时间）。

#### 2.3.1 每轮上下文（精简后长什么样）

以前提示词让执行者直接整份读 `state.json`（几百 KB、含整段验收文字），每轮都要付一遍 token。现在分三级：

1. **现状摘要**（提示词内，6–8 行）：状态、当前阶段、阻塞 id 与理由、有未完成项的阶段及数量、3 条待做示例。由 `fillPrompt()` 用 `{{SNAPSHOT}}` 注入，来源是 `PLAN-INDEX.json`，过期就现算。
2. **`pipeline/PLAN-INDEX.json`**（约 2 KB）：每阶段一行（状态 / 待做数 / 已完成数含归档 / 首个待做项），模型要看全局时读它。
3. **`pipeline/state.json`**：仍然唯一事实源，但只在「真要改某个子项」时读对应阶段。

`PLAN-INDEX.json` 由调度器在空闲窗口（等下一拍 / 预检拦停 / 一轮刚落）刷新，和 done 归档共用同一个维护钩子；内容没变就不重写。它是只读派生文件，不参与任何判定，删掉也会自动重建，**不影响流水线行为**。送审与审稿相关的提示词段落没有改动。

### 2.4 预算与额度

`pipeline/budget.json` 控制单轮上限：

- 每轮 **40 次模型调用 / 200k 上下文**；32 次预警，36 次后**禁止开新块**，40 次或触顶必须收尾
- 主控段 120k / 80 次
- 工具输出：成功 1600 字、失败 6000 字（超长会被截断）

面板与 Wiki 显示的「上下文 68%」「22/40」即来自这里。**逼近上限不是错误，是设计**：逼本轮收尾而不是硬撑。

**物理送审次数有独立的账**：`pipeline/budget.json` 的 `review` 段按送审 scope 计数（账本在 `pipeline/review/attempts.json`），分 L1（fast）与 L2（review）两档：

- 默认上限 **L1 = 5 次、L2 = 10 次**；项目可用 `review.scope_overrides.<scope>.l1_max_physical_submissions` / `l2_max_physical_submissions` 单独覆盖（second 现在 `ops` L2=10、`gold` L2=20）
- 计数到顶时该 scope 的任务被判「物理封顶」，调度**不再自动选中它**，转人工；流水线详情里出现逐行额度表（scope / 已用 / 上限 / 追加次数 / 追加后），封顶行标红
- 追加额度只写 `scope_overrides` 并追加一条审计（`<root>/.aris-run/quota-decisions.jsonl`，滚动保留 200 条），**不清 block、不起轮**；点「追加额度并批准重启」才会同时放行下一轮
- 追加是幂等的（同 directiveId + scope + 档位重复提交不会重复加）；新上限必须大于已用次数，且 ≤ 10000

**余额与 GPT 额度是缓存读数**：两个面板都不实时查账，读的是后端缓存的快照（`balance.at` / `quota.at`）。面板会显示「N 分钟前」，超过阈值加「可能过期」——看到这两个字样时，先点该页的「立即更新」（余额）或「刷新」再下结论，不要把旧数字当实时余额。

## 3. `Aris_Dsh` 面板（写面）

侧栏点 `Aris_Dsh`。顶部五个页签：**总览 / 流水线 / 产物 / 审核 / 设置**，默认落在「总览」。

四条贯穿全面板的约定：

- **列表一律表格化**：列多的表在窄屏横向滚动，表头行固定、总表的状态列固定；点一行，详情在**表格下方**展开，不在行内摊开。
- **多流水线**：页内用 chips 直接切换流水线，不必先回总览。总表按状态排序：错误 / 需人工 → 运行中 → 待审（等待审核）→ 停止。
- **大分组默认折叠**：点分组标题行展开/收起，页头常驻「展开全部 / 收起全部」。单条流水线的详情页默认展开。
- **自动刷新**：默认每 10 秒轮询一次，页头可关。后端连不上时页头明说「断连」并给最后成功时间，**不再**把上一次的数据当实时数据继续显示（见 §9）。写动作成功后前端会强制重拉一次快照，不等下一次轮询；余额与 GPT 额度这类缓存读数会顺带刷新时间戳。

### 3.1 总览

**看什么**

1. **顶部 KPI**（8 个）：在跑 / 需人工 / 等审核 / 等回件 / 今日轮数（副文案带「上限 ¥N · 已用 x%」）/ 今日成本 / 累计 / 余额（副文案带阈值，页头另有「N 分钟前」读数时间）。下方两张横条按流水线并列「今日轮次 / 今日成本」，点流水线名直接跳到该条详情。
2. **筛选 chips**：全部 / 在跑 / 需人工 / 已停止；同一行右侧是搜索框（按流水线名与项目路径过滤）。
3. **一张总表**：所有已登记的流水线，一行一条。

总表各列：

| 列 | 含义 |
|---|---|
| 状态 | 状态词，见 §3.2.2。排序权重：错误 / 需人工 → 运行中 → 等待审核 → 停止。审稿侧有待裁决的流水线一律算「需人工」，即使进程还在跑（「现在」列会写 `运行中 · …`） |
| 流水线 | 项目名（添加时登记的根目录） |
| 阶段 | 当前阶段：`序号/11 · 中文阶段名 · 状态机 id`，如 `6/11 · 4-B 混合规划 · S4b_plan` |
| 现在 | 在跑：`本轮 09:38 起 · 已跑 15 分钟 · 110/60 步 · 上下文 39%`；没在跑时显示上一轮同一组数 |
| 门禁 | `已裁 M/总数`，附最近一条裁决词（`GO` / `NO_GO_…`） |
| 阻碍 | 最严重一条的短句；红=需人工、琥珀=注意、灰=信息，多条时补 `+N` |
| 审核 | `在途 N` + 最近一次 `verdict · score/10` |
| 成本 | `上轮 ¥x` / `累计 ¥y · N 轮` |
| 下轮 | 两行：上行是预计起下一轮的时间（运行中写「本轮结束后」），下行是状态（按间隔 / 等 GPT 额度 / 等 Kimi 回件 / 未排期 / 已停用） |

「下轮」下行的状态词（判定逻辑与旧版摘要行相同，只是现在长在总表一列里）：

| 状态 | 含义 |
|---|---|
| 按间隔 | 没有在途、没有额度拦，按节拍起；上行就是 `MM-DD HH:MM` |
| 等 Kimi 回件 | 有邮箱在途审稿，回件前不会起新轮；上行是预估回件后才起的时间 |
| 等 GPT 额度 | 本小时 GPT 派单额度已用完，排在额度恢复点（滑出窗口那一刻），不早于「结束时间 + 间隔」 |
| 跑完按间隔 / 本轮结束后 | 这一轮正在跑；上行写「本轮结束后」，跑完才按间隔排下一轮 |
| 未排期 / 已停用 | 起轮器还没算出下一次 / 这条流水线没启用 |

> 状态取 `nextAtBasis`：`interval` / `mailbox` / `quota` / `quota-stuck`（额度用了但探不到恢复点，写「等额度恢复」）。

**能做什么**：只读浏览。点行 → 该流水线的详情在表下方展开（和 §3.2 的详情同一个）；再点收起。要动手（启用、跑一轮、停止……）进「流水线」页签。

**「需要人处理」何时消失**：点「提交并批准重启」后，`.aris-run/human-note.md` 会记一条带时间的人工回复（**新一轮只注入最新一条**，更早的进 `state.user_directives` 归档，不再整段拼提示词）；凡是 `at` 早于这条回复的「需人工」条目（封顶转人工、连败、多轮退回、等待人工）都不再列出——回复即答复。之后要再出现两版新退回才重新提示（只多算一版不重复打扰）；「提交并批准重启」会当场起一轮（若已有轮次在跑，则提示「本轮进行中」，不会并发起两轮）。

「多轮退回」这类软提醒不重复轰炸：答复之后，同一份稿子**再退回两版**才会重新提一次；在那之前面板保持安静，免得每起一轮就弹同一个建议。

**操作分级**：整页 L0（§3.6）。

**窄屏**：表格横向滚动，表头行吸顶、状态列固定在左侧，滑到右边也知道自己在看哪一行。

### 3.2 流水线

**看什么**：列表（表格）＋点行在表格下方展开的单条详情（§3.2.3）。

**能做什么**：添加 / 移除流水线、启用停用、运行一次、停止、检查回复 / 检查恢复、清空运行记录、看日志与会话——逐条见 §3.2.4。

**操作分级**：本页 L0–L3 齐全，是唯一会改动东西的页签。

#### 3.2.1 列表

顶部可添加流水线：填项目根目录 → 「添加」→ 选 driver（`auto` 会识别 `frrs` 或通用 `aris`）。

表格列与总览完全一致（状态 / 流水线 / 阶段 / 现在 / 门禁 / 阻碍 / 审核 / 成本 / 下轮），按状态排序；点行在表格下方展开该条详情。

表内另有两个提示徽章，只在有事时出现：

| 徽章 | 含义 |
|---|---|
| `未送审 N 轮` | 连续 N 轮没有送审（评审空转，提示你去查额度或 gate） |
| `Kimi 未取件 N 分钟` | 最老的待回件已等 N 分钟，超过阈值 → 检查 Kimi 定时任务是否在跑 |

#### 3.2.2 状态词义

| 状态 | 含义 |
|---|---|
| 待命 | 已启用，等节拍起下一轮 |
| 正在运行 | 有一个 headless 子进程正在跑本轮 |
| 等待审核 | 在途审稿 ≥1 条，回件之前不会起新轮（省 token） |
| 需人工 | 本轮被 `blocked_on_user` 卡住、state 里登记了 block，或审稿侧点名要人处理（封顶 / 多轮退回 / 等待人工）。后一种情况流水线可能还在跑，此时「现在」列写成 `运行中 · …`，两处口径一致 |
| 等额度 | GPT/Codex **小时额度用尽**（不是物理送审次数封顶）：调度把「下轮」排到额度恢复时刻，期间**不启新一轮**、不送审、不占送审次数，恢复后自动继续，不需要人裁决。判定见 `bin/lib/aris-runner.mjs` 的 `isQuotaBlock()`；带 `attempts 15/15`、`物理送审额度` 字样的仍算「需人工」。审核页顶部会显示琥珀提示条「本小时额度用完，HH:MM 之后自动恢复」 |
| 停止中 | 已登记停止：本轮跑完即停，不中断 |
| 已停止 | 已禁用，不会自动起轮（在途审稿回件也不起） |
| 出错 | 连续失败/启动失败，看日志 |

这套状态词与 `Aris_Wiki` 共用同一套判定（§4.2），两个面板对同一件事说同一句话。

#### 3.2.3 单条详情

点一行进入**独立详情视图**（不再是表下方展开）：顶部「← 全部流水线」返回，右侧一排全流水线 chips，点名字直接换一条看。

**详情页头**：状态徽标 · 流水线名 · driver · 模型 · 间隔；右侧「看日志 / 看会话 / 提示词」。下一行：当前阶段 + 阶段进度条（已完成 / 进行中 / 待开始）+ 门禁 `d/t` + 下轮时间 + 今日轮数·成本，最右是路径。

**两栏等宽**（窄屏退单列）：

| 左栏 | 右栏 |
|---|---|
| **每轮指标**：成本 / 步数 / 耗时三选一，三档 y 轴、均值虚线、`#n` 标签、底部「合计 / 均值 / 最高 / 共 N 轮」；超过 24 轮横向滚 | **最新审核回件**：最近一次送审的回件与结论 |
| **现在**：模型、步数、开始时间、累计分钟、上下文 %、会话 id，加当前动作摘要 | **阶段树**：与「计划项」读同一份阶段、同一顺序，**一个阶段一行**（S4a/S4b/S4c/S4d 各占一行，不再收进虚构的 S4 父节点）；状态点 + 完成数，点开看未完成项（最多 6 条） |
| **计划项**：按阶段分组，组头「阶段名 · N 项 · 完成 x/y · 已完成 k 项」，逐项标已完成 / 待办；每组下方「已完成 k 项」列出 state.json 的 `states[].done`（只增不删；归档后只列最近 10 条，更早在 `pipeline/done-archive.json`） | **总计划**：完成百分比 + 当前阶段/状态 + 进度条 |
|  | **轮次历史**：轮次 · 开始 · 步数 · 成本 · 结论 · 退出码（最近 20 轮；2026-11-20 起位于右栏） |
|  | **最近事件**：时间 · 类型 · 内容，无事件时不显示 |

每块都是可折叠段，详情默认全展开；右栏整体 sticky，随页面滚动常驻。

详情里还有两块专门给「人」用，位置固定在「当前任务」与两栏之间：

- **执行者与审稿者**（折叠，标题右侧显示当前组合，如「deepseek-flash → GPT」）：执行者三选一 `跟随工作区 / DSH / Kimi A/B 双节拍`，改选后出现「确认交接本项目」；DSH 审稿槽 `Kimi 邮箱 / GPT 外审`，工作区线路不是「自动」时置灰，并提示去设置页切成「自动」
- **需要人工介入**（受阻时出现）：阻碍原因 + 建议 + 额度表（常显全部 scope，封顶的排最前）+「最近裁决」；按钮依次「追加额度并批准重启（N 项）」「只保存额度」「只留备注」「复制摘要另开对话」底部是「操作 · 按影响分级」（L0–L3，见 §3.2.4 与 §3.6）。

> **done 归档**：`done` 只增不删，长期运行会把 `state.json` 撑到几百 KB（超过读取上限会让预检异常）。
>
> **自动**：调度器在三种空闲窗口顺手归档——① 无事可做、等下一次节拍；② 预检拦停（等人工 / 等额度 / 在途审稿）；③ 一轮刚结束。条件是 `state.json` ≥ 380 KB 且距上次归档超过 6 小时；每阶段只留最近 10 条，写盘用临时文件 + 原子替换，备份留在 `.aris-run/state.json.bak-*`（最多 3 份），归档结果记进 `aris-events.jsonl`。归档失败只记日志，不拦调度。
>
> **手动**：`node bin/aris-archive-done.mjs <root> [--keep 10] --apply`（默认 dry-run）。
>
> 两种方式都只动 `states[].done`，绝不碰 `todo` / `status` / 门禁；面板与 wiki 的「已完成 k 项」按 `done.length + doneArchived` 统计，明细只列最近 10 条，更早在 `pipeline/done-archive.json`。

旧五块写法（正在做什么 / 总计划·计划与事件 / 图表 / 运行数据 / 操作）自 2026-11-19 起作废。



#### 3.2.4 操作

操作分四档（汇总表见 §3.6）：L0 只读、L1 可逆、L2 阻断（行内二次确认）、L3 破坏（「危险操作」区，默认收起）。

| 操作 | 作用 | 级别 | 注意 |
|---|---|---|---|
| 启用 | 打开自动节拍：点一下会真的起一轮（花额度、写产物） | L2 | 行内二次确认（点一次变「确认启用」，再点才执行） |
| 停用 | 关闭自动节拍 | L2 | 停用后**在途审稿回件也不会起轮**；重新启用要手动点或等下一次节拍 |
| 运行一次 | 立刻起一轮（不看 `nextAt`） | L1 | 已有进程在跑时不可用 |
| 停止 | 登记「本轮跑完即停」 | L2 | 不中断当前轮，避免半截提交 |
| 取消停止 | 撤回停止意图 | L1 | — |
| 强制停止 | 立刻杀本轮进程 | L3 | 可能留下未提交改动、审查请求未回写；gate 租约会 70 分钟后自然过期 |
| 检查回复 | 收件：把 `out/` 的回复收进 `.aris/reviews/` | L1 | 只读 inbox/outbox，不改 state |
| 检查恢复 | 把「显示运行中但进程已消失」的回合标为中断 | L1 | 只修运行时记录 |
| 清空运行记录 | 把运行记录、费用台账归档到 `.aris-run/history` 并清零面板统计 | L2 | 不影响 state 与论文产物；归档后图表只剩归档之后的轮次（§3.7） |
| 提示词 / 重置提示词 | 查看/恢复本轮提示词模板 | 看 L0 / 重置 L2 | 重置只影响后续轮次，旧模板先自己留档 |
| 日志 | 打开最近日志 | L0 | — |
| 会话 | 只读查看本轮 headless 会话（提问、工具调用、结果） | L0 | 运行中按钮显示「会话 · 运行中」并带「运行中 · headless 持有」标签，**不要在里面发消息**（会和 headless 抢写同一会话日志） |
| 移除 | 从面板移除这条流水线登记 | L3 | 不删项目文件，只是不再监控；需手打流水线名 |

> 旧版按「按钮颜色」记风险的说法**已作废**。现在一律看级别：绿色/蓝色只表示样式，不承载「这个是危险操作」的含义；危险项集中在详情底部的「危险操作」区，默认收起。

### 3.3 产物

**看什么**：主论文卡、各目录编译状态与首个错误、引用体检、「产物文件表（左）＋预览（右）」。

**能做什么**：打开文件 / 看源码 / 复制路径（L0）、拖分隔条调宽（L0，双击复位，宽度记忆）、编译论文（L1）。

- **主论文**卡固定置顶：显示 `label · 文件名`、体积、生成时间，按钮「打开 PDF」「看源码」「编译论文」
- **编译论文**：调用 `bin/paper-build.mjs`，自动判引擎（有 `ctex/xeCJK/fontspec` → xelatex，否则 pdflatex），PDF 写到各目录 `build/`；面板逐目录显示「通过 xelatex 23 页 / 失败 + 首个错误」
- **引用体检**：`未被引用 N`、`缺失 N`、`空章 N`（解析 `\includegraphics` 与章节字数）

**文件表 + 预览**（本页下半部分）：

- 左侧是**文件表**，按组列（论文 / 图 / 实验 / 审查 / 运行 / 幻灯片）；左表与右侧预览一起撑满页签高度（短内容也到底，不悬在半空），表格自身滚动、表头吸顶
- 点一行，右侧出预览；中间有**拖拽条**调宽，双击复位，宽度记忆在本地（下次打开还是这个宽度）
- 窄屏退成单列，预览移到表格**上方**
- 预览：文本按骨架渲染（先看标题与段落结构，不把整篇塞进面板）、图片直接显示、**PDF 用 iframe 内嵌并撑满预览区**；PDF 体积超过后端上限（4MB）时只给「打开原文件」，不再留一块空白提示条；读不了的给占位，用「打开原文件」或「复制路径」带走

六组只读浏览的另一份在 `Aris_Wiki` 的「产物」页（§4.3），同一套扫描。

**操作分级**：浏览与预览 L0；「编译论文」L1（可重跑，产物落 `build/`）。

### 3.4 审核

Kimi 邮箱与 ChatGPT 后台是同一件事的两条通道，现在同页分成**两个大类**，各自嵌套子分组；页内分组一律默认折叠，点标题行展开，页头「展开全部 / 收起全部」。

**看什么**：下面这棵树就是全页骨架——两条通道的配置、待人工裁决、稿件审核记录、审核锁、两张环形图。

页面顶部另有「统计与列表范围」chips（全部 / 各流水线）：选中后**两张环形图与稿件列表同时按该流水线过滤**，右侧 tag 显示当前范围与份数；「稿件审核记录」本身是可折叠段（默认展开，点标题行收起）。

**能做什么**：改通道配置与提示词（保存 L1）、立即收件（L1）、手动派单（L1）、裁决（「提交并批准重启」L2 /「只留备注」L1 /「复制摘要另开对话」L0）、释放审核锁（L2）。逐项分级见各小节与 §3.6。

```
审核
├─ Kimi 邮箱
│   ├─ 执行权            ← 线路三选一、双槽、handoff
│   ├─ 邮箱与收件        ← 在途请求、立即收件
│   ├─ 取件节奏          ← 间隔与起始时间
│   └─ 取件提示词        ← 给 Kimi 客户端用的整段提示词
├─ ChatGPT 后台
│   ├─ 通道状态与额度
│   ├─ 派单工作区
│   ├─ 送审提示词
│   ├─ 任务分类
│   ├─ 手动派单
│   └─ 最近调用
├─ 待人工裁决            ← 只做定位，裁决去该流水线详情
├─ 稿件审核记录          ← 按稿归并的审稿产物
├─ 审核锁                ← 单飞证据与锁位置
└─ 结论分布 / 通道分布   ← 两张环形图（§3.7）
```

#### 3.4.1 Kimi 邮箱

**执行权**

- **审核线路**：三选一。面板是**唯一写入点**：保存时同时写两处并回读校验——
  ① `<工作区>/.dsh/aris-dashboard.json` 的 `external.review.channel`（DSH 侧闸门读它）
  ② 每个项目 `<root>/.aris/reviewer.json`（流水线自己的送审入口读它）
  - `auto`：跟随项目 `reviewer.json` 的 `active`（切来切去之后的安全默认）
  - `kimi`：只走邮箱；面板「派单」与 CLI `--via codex` 会被直接拒，并提示去改线路
  - `gpt`：只走 GPT；邮箱投递（`aris-review --enqueue`）会被直接拒
  - 闸门是同步的：面板派单立刻回错误，不占小时额度、不拉起 codex
- **双槽保留**：`reviewer.json` 里两套槽位都存着（`channels.kimi` / `channels.gpt`），`reviewers[]` 只放当前生效那套。切换线路是把当前槽归位、把目标槽铺出来，所以 **kimi ⇄ gpt 来回切不会丢配置**（`tier`、`timeoutSec`、任务分类都在）
- **项目侧是否同步**：线路卡下方列出每个项目的实际 `active`。出现琥珀色标签说明该项目 `reviewer.json` 还没跟上（保存失败或手工改过），点一次线路按钮即可同步；不同步时面板只影响 DSH 侧派单，流水线自己的送审仍按项目配置走
- **流水线送审入口按面板走**：`Frrs/second` 的 `pipeline/review/mailbox_bridge.py` 先读面板：`gpt` 时同步调 `node bin/aris-review.mjs --via codex --task <分类>` 并把评论落到流水线期待的结果文件；`kimi` 时保留邮箱桥（投递 + 刷 `queue.md`）；`auto` 跟随项目 `active`。**GPT 送审失败不降级到邮箱**，直接报错退出，避免「以为走了 GPT 其实又进了邮箱」
- **运行期锁定**：只要有流水线在跑（`pipelines[].running`），审核线路就被锁住，切到别的通道会直接被拒（同值保存仍放行）。面板上其余两个按钮置灰并给出原因，服务端也做同样的判断——跑到一半换通道会造成同一轮出现两种审稿人。等这一轮结束再改
- **DSH 接管 / 交回 Kimi Work**：切换 `handoff.mode`
  - `dsh`：节拍器在 DSH 里自动起轮（推荐，本机常开时用这个）
  - `kimi`：不在 DSH 起轮，改由 Kimi 侧定时任务拉起

**邮箱与收件**

- 邮箱协议：请求进 `…\kimi\aris-mailbox\in\<时间>-slot<N>.request.md`，Kimi 桌面客户端取件作答，回复落 `out\`
- **立即收件** = **检查回复** = CLI `--collect`：把 `out/` 的回复收进 `.aris/reviews/`，记 `verdict`、`score`、`identity`
- 在途判定与 dsh 流水线同源（`bin/lib/aris-runner.mjs` 的 `pendingReviews`）：邮箱索引 `projects.json` + 在途请求文件双条件

**取件节奏**

- 「Kimi 间隔 / 起始时间」决定提示词里的取件节奏与起点；必须与 Kimi 应用内定时任务**一致**
- 超阈值判定 = `max(30, 2×Kimi 取件周期)` 分钟（当前周期 15 分钟 → 30 分钟）；超了只标「已超阈值，Kimi 可能没取件」，不转人工

**取件提示词**

- 给 Kimi 桌面客户端用的整段提示词，含邮箱路径、间隔、该模型自报 `Reviewer-Model`
- 「复制 / 存到文件」把提示词带走

> Kimi 侧没有 API、没有 CLI，只能靠应用内定时任务 + 邮箱。Kimi 应用关掉时任务不跑，所以「Kimi 未取件 N 分钟」是唯一可靠信号。

#### 3.4.2 ChatGPT 后台

**通道状态与额度**

**订阅额度**（通道卡里「订阅额度」一行）：Codex 每次运行都会把服务端返回的 `rate_limits` 写进会话 rollout（`~/.codex/sessions/<年>/<月>/<日>/rollout-*.jsonl`），面板读最近一份并显示 5 小时窗口与周窗口的已用百分比、距重置时间。三点说明：

- 这是**账户真实额度**，与面板下方「每小时 N 次」是我这边的闸门，两套数字分开看，别混成一条
- 只在**跑过派单之后**才更新；那行会标「取自 N 分钟前那次派单」，超过 5 小时标「可能已过期」
- 字段属 CLI 内部结构而非公开 API，读不到时降级显示原因（不报错、不影响派单）；实现见 `bin/lib/codex-quota.mjs`

**额度用完时的下一轮**：面板「每小时 N 次」用完时，`quotaGate` 会算出窗口里最早那次调用滑出的时刻（`calls[used-limit] + 1 小时`），流水线「下轮」跳到该时刻并标「等 GPT 额度」。三点：

- 只影响**调度**，不影响手动派单：手动点「派单」仍立刻尝试，被额度挡住时直接回原因
- 线路设成 `kimi` 时不看 GPT 额度（Kimi 走邮箱，不消耗 Codex 的 4 次/小时）
- 连续失败 3 次的停摆没有时间点，`nextAt` 留空、状态显示「等待人工」；到 `/api` 或面板恢复后重新起算；实现见 `bin/lib/codex-review.mjs` 的 `quotaGate()`、`bin/lib/aris-runner.mjs` 的 `nextRunAt(..., { blockedUntil })` 与 `recalcNextAt`

不另开 API key，直接用这台机器上装好的 Codex/ChatGPT 桌面端（订阅登录）当第三个审稿族。本组卡片默认折叠，点标题行展开。

**通道卡（状态与启停分开）**

| 字段 | 含义 | 默认 |
|---|---|---|
| 状态徽标 | `● 已启用`（绿）/ `○ 已停用`（灰）——只表示当前状态，不可点 | — |
| 启用 / 停用 | 独立按钮，点一下切换 `external.codex.enabled`，关掉后所有派单一律拒 | 关 |
| 每小时上限 | 滑动 60 分钟内的调用次数上限 | 4 |
| 每日上限 | `0` = 不限 | 0 |
| 单次超时 | 超时即 kill | 8 分钟 |
| 代理 | codex 走 HTTPS，直连 chatgpt.com 不通 | `http://127.0.0.1:7897` |
| 沙箱 | `read-only` 只把送审材料喂进去；`danger-full-access` 才让它自己读工程 | `read-only` |
| 会话库占用 | `~/.codex/sessions` 的文件数与体积；**只报不删**，要清自己动手 | — |

- **`codex.exe` 是否找到**：`WindowsApps` 目录不可枚举（EPERM），所以走 `Get-AppxPackage OpenAI.Codex` 取安装位；版本升级后自动跟到新目录
- **本小时剩余 / 连续失败**：口径与预算文件 `.dsh/codex-budget.json` 一致；连续失败 3 次自动停摆，需在面板手动恢复
- **保存即回读**：保存后显示的是从磁盘重读的配置，不是前端乐观回显

**任务分类 → 模型**（按「这一单要审什么」分档，不绑流水线阶段：阶段会变，任务类型稳定）

| 任务分类 | 默认模型 | 强度 | 用在哪 |
|---|---|---|---|
| `format_check` 格式/数据核对 | `gpt-6-luna` | low | 章节齐全、数字前后一致、表格字段对得上 |
| `routine_review` 常规审查 | `gpt-6.2-sol` | medium | 日常文档与改动审查（默认） |
| `deep_attack` 深度论证攻击 | `gpt-6.2-astra` | high | 找致命反驳、跨材料综合、大改方案审读 |
| `claim_audit` 论点—证据核对 | `gpt-6.1-terra` | medium | 逐条结论回原文找证据，要读图与版面 |
| `citation_audit` 引用与元数据 | `gpt-6-luna` | low | bib / DOI / 页码 / 作者顺序比对 |
| `layout_check` 版面与图表 | `gpt-6.1-terra` | medium | 排版、图注、图内文字可读性 |
| `writing_review` 写作与结构审读 | `gpt-6.2-sol` | medium | 行文、章节结构、读者可理解性 |

旧的「环节」配置（`external.codex.stages`，S1…S6）读配置时会自动按表迁移到任务分类：S1/S2→`format_check`、S3/S4→`routine_review`、S5→`deep_attack`、S6→`writing_review`、`kill_argument`→`deep_attack`。迁移后只写 `external.codex.tasks`，不再保留旧键。

**派单工作区**：决定 `-C` 指向哪，也就决定 ChatGPT 续聊时还能看到什么。

| 模式 | `-C` 指向 | 续聊视野 | 用途 |
|---|---|---|---|
| `root` 项目根（默认） | 项目根 | 整个项目 | 常规审稿，材料分散在多个目录 |
| `subdir` 指定子目录 | `<项目根>/<子目录>` | 只有该子目录 | 只审 `dataset_gen/` 这类材料，省 token |
| `copy` 隔离副本 | `<工作区>/tmp/codex-sandbox/<时间>/` | 只有副本 | 不想让它看到项目其余部分 |

- 子目录必须存在且在项目内（拒绝绝对路径、`..` 逃逸）；`copy` 只复制本次送审文件，**跑完自动删副本**（`cleanCopy`，可在配置里关）
- 三种模式下，会话与产物仍写在 `<项目>/.aris-run/codex/`，面板按项目聚合，不会散落

**送审提示词（可改、可预览）**：真正发出去的内容就是这两段渲染后的结果。

| 段 | 作用 | 可改 |
|---|---|---|
| `role` 角色段 | 身份、任务分类、只读硬规则 4 条、送审材料清单 | 是 |
| `output` 输出段 | `Reviewer-Model:` 头、`VERDICT`、`Score: n/10`、摘要/主要问题/次要问题/建议 | 是 |

- 占位符：`{{model}}` `{{effort}}` `{{taskKey}}` `{{taskLabel}}` `{{taskHint}}` `{{access}}` `{{cwd}}` `{{fileCount}}` `{{chars}}` `{{files}}` `{{date}}`
- 面板下方常驻「渲染预览（样例材料）」——看到的就是模板展开后的样子；写了未定义的占位符会红字提示（会被原样发出去）
- 「恢复默认内容」把两段填回出厂模板；「保存提示词」写入 `external.codex.prompt`，下一次派单立即生效
- 实际发送的完整提示词还有第三份留档：`<项目>/.aris-run/codex/<时间>-<任务分类>.task.md`（逐字，含材料正文）

**手动派单**：选流水线根 → 送审文件清单（一行一个相对路径，支持 `*` 通配，最多 8 个文件、单文件超 6 万字符截断并提示）→ 选任务分类 → 派单。后台跑，结果落 `<项目>/.aris/reviews/<时间>-codex-<任务分类>.md`，面板展示上次结果的模型/tokens/耗时/字符数/文件数/结论。

**最近调用**：每次的时间/任务分类/模型/成败/tokens/耗时，带「续聊」按钮直接复制命令；明细在 `.dsh/codex-runs.jsonl`（字段 `task`、`sessionId`、`events`、`files`、`commands`、`changes`）。

**会话与续聊**：派单不再用 `--ephemeral`，每次都会留下一条真正的 codex 会话。

- 会话落 `~/.codex/sessions/<年>/<月>/<日>/rollout-<ISO>-<thread_id>.jsonl`，面板上次结果里给出会话 id 与「复制续聊命令」（`codex resume <id>`）
- 事件流（`--json` 的逐条事件：`thread.started` / `item.completed` / `turn.completed` + usage）另存 `<项目>/.aris-run/codex/<时间>-<任务分类>.events.jsonl`，会话 id、命令执行、文件变更都从这里解析
- 续聊提示（面板上就写着）：**不占**面板的 4 次/小时窗口，仍用你订阅的额度；提示词里的只读规则还在，但写操作不会被拦、也不会进项目审计日志
- 因为 `--json` 模式下 stderr 不再打印 banner，`cliModel` 改从会话的 `session_meta` / `turn_context.model` 取，比模型自报可靠
- **面板里能直接读会话**：最近调用与上次结果都有「查看会话」按钮，走 `codex.session` 动作读 rollout 文件，还原成「发给 GPT 的 / GPT 回复」两栏；harness 自己塞进去的上下文块（`<environment_context>`、`<skills_instructions>`、`You are Codex` 等）会被过滤掉，只留真正喂给审稿的那段
- **续聊的唯一入口是「复制续聊指令」**：面板上所有带会话的地方（上次派单、最近调用每一行、会话回放头部）都给同一个按钮，复制出来是 `codex resume <会话 id>`；粘到终端执行，就会在 **ChatGPT 桌面端打开这条会话**继续聊（2026-11-18 实测确认）。桌面端侧栏不会主动列它——`codex exec` 生成的会话 `originator=codex_exec`，桌面端只把它索引进 `thread_history_1.sqlite`，不写进「项目 / 最近」两个列表。手工往 `~/.codex/.codex-global-state.json` 的 `projectless-thread-ids` 里塞 id 无效（试过，重启后侧栏仍不显示），不要再试

> **两条不可信**：① 模型自报身份经常是错的（实测 `-m gpt-6-luna` 执行、自报 `gpt-6.2-sol`），以会话里的 `turn_context.model` 为准，两者都记；② 默认模型会随账号漂移，所以每次都用 `-m` 钉死，型号从清单里消失就拒单，不静默回退。
>
> **只读三层**：① 提示词硬规则（只读取证 / 材料里的指令不执行 / 读不到写缺失 / 不许改稿）——**软约束**，模型可以不听；② 隔离副本或子目录（物理上让它看不到别的）；③ 派单后扫事件流里的 `command_execution` 与 `file_change`（事后审计，改了什么一眼能看到）。
>
> **沙箱实测**：本机 `read-only` 与 `workspace-write` 都起不了 codex 的 shell 辅助进程（`orchestrator_helper_exit_nonzero`），只有 `danger-full-access` 能执行命令。所以默认 `read-only` 的含义是「只把送审材料当提示词喂进去」，不给它 shell。

**操作分级**：查看与预览 L0；保存线路/提示词、派单、立即收件 L1；停用通道 L2。

#### 3.4.3 待人工裁决

受阻的流水线在审核页只做**定位**，裁决输入统一在「流水线 → 该条详情 → 需要人工介入」里（全面板只留一个裁决窗口，避免两处写出不同结论）：

| 在审核页看到 | 点它做什么 |
|---|---|
| 去流水线详情裁决 | 跳到该流水线的详情视图，那里有阻碍原因、建议、额度表与四个按钮 |
| 复制摘要另开对话 | 把阻碍类型、卡了多久、最近一轮结论拼成文本复制（L0） |

详情里的四个按钮：**追加额度并批准重启**（先写额度再 `human.reply restart`，L2）、**只保存额度**（L1）、**只留备注**（L1）、**复制摘要另开对话**（L0）。裁决前先看证据——面板不替你判断该不该放行。

**审稿意见按 MUST / SHOULD 计数**：最新一轮审稿返回后，凡显示审核结论的位置都同时给条数——流水线表的「审核」列、审核页表格结论徽标下方、展开行的段头、审核页「结论分布」角标（`N 份 · MUST x · SHOULD y`）、详情右栏「结论分布」标题。计数来自 `bin/lib/review-results.mjs` 的 `sectionCounts()`：按 `## MUST` / `## SHOULD` / `## OPTIONAL` 段统计条目，Kimi 用「主要问题 / 次要问题」时按这两段统计（`主要问题` 视作 MUST）。

#### 3.4.4 「需人工」到底列什么

面板只在机器**自己不会再往下走**的时候把人叫出来，不是拿总数吓人：

| 触发 | 出现在 | 处置 |
|---|---|---|
| `pipeline/state.json` 的 `block` 存在（如 `gold-review-cap-5of5-…`） | 红 · 人工 | 点「打开清单」看 `block.manual_checklist`，处理完再恢复 |
| `.aris/review-cap.json` 存在（同一 scope 送审到顶仍未过） | 红 · 人工 | 看 `cap-review_<scope>_<ts>.md` 清单，人工定稿或调方向 |
| `runtime.json` 的 `status = blocked_on_user` | 红 · 人工 | 看 `blockedReason`，改完再「启用」 |
| 最新一轮 `reject` | 红 · 人工 | 整段重做，别在旧稿上补 |
| 同一 scope 已改 ≥ 5 轮仍是 `revise` | 琥珀 · 注意 | 多半是方向性问题，人工看一眼再让它改 |
| GPT 额度用完 / 连续 3 次失败停摆 | 琥珀 / 红 | 等窗口恢复，或到「ChatGPT 后台」卡手动恢复 |
| 流水线被停用（`config.enabled = false`） | 琥珀 · 注意 | 确认是否要恢复自动起轮 |

其余 `待修` 都不进这张表——那是流水线下一轮要干的活，不是人干的活。

同一 scope 已经有封顶事件时，不再重复报「已改 ≥ 5 轮」。红（真动手）排在琥珀（看着点）前面。

#### 3.4.5 稿件审核记录

把各流水线 `<root>/.aris/reviews/` 里的审稿产物统一汇总到一处，表格化展示：

- **按稿归并**：一份稿子改三轮就有三条记录，这里按「项目 + `scope`」归组，只把最新一轮摆出来；`scope` 从 `target` 的 `review_package_<scope>_rN.md` 推，推不出时退回任务分类或文件名
- 顶部三个数：`需人工 N`（红/绿）、`当前待修 M 个 scope`（琥珀）、`已通过 K`（绿），右边补 `稿件 X 份 / 记录 Y 条`——**Y 是历史累加，不是欠账**
- 筛选两行可叠加：结论（全部 / 通过 / 待修 / 退回 / 未判定）与通道（两条通道 / Kimi / GPT / 未标注），数字按**最新口径**算
- 每行（表格列）：时间 · 项目 · `scope` · 结论徽标 · `score/10` · `第 N 轮 · 历史 M 条` · 通道 · 模型
- 点一行，详情在表格下方展开：摘要 → `必须解决（N 条）`（Kimi 的 `## MUST`、GPT 模板的 `## 主要问题`）→ 「历史 M 条」逐轮列出 → 懒加载读原文
- 数据来源：结构化 `*.json` 优先取字段；只有 `*-codex-*.md` 时正则抠模型、`VERDICT:`、`Score:`、`## 摘要`
- 通道归属是推断的：`backend` 优先（`codex`→GPT，`mailbox`/`kimi`→Kimi），缺失时看身份串里的 kimi/moonshot/gpt/openai
- 只汇总最近 100 条（全量在各自 `.aris/reviews/`）

#### 3.4.6 审核锁

- **单飞规则**：两条通道共用一把审核锁 `<工作区>/.dsh/.review.lock`，同一时刻只允许一次审核在跑。Kimi 投递时占锁、收件时解锁；GPT 派单时占锁、跑完解锁。锁被占时再投递/再派单会被直接拒绝，并告诉你锁在谁手里、多久前开始
- **审核通道卡**（本组顶部）：显示当前锁状态（空闲 / 运行中：通道 · 任务 · 目标）
- 锁 TTL：Kimi 6 小时、GPT 单次超时 + 1 分钟

两张环形图，口径与「稿件审核记录」同一套（按稿归并后的最新一轮），读法见 §3.7。切了线路之后想确认生效，看「通道分布」比翻记录快。

### 3.5 设置

设置页按「和谁有关」自上而下排列：审核线路 → GPT 后台启停 → 流水线运行设置 → 邮箱与运行参数 → 环境信息。

| 审核线路 | 全局三选一（自动 / Kimi 邮箱 / GPT 外审）。选「自动」后，逐项目审稿槽才可改 |

### 3.6 操作分级 L0–L3

所有按钮和命令都按「会不会丢东西、会不会打断在途工作」分成四档，颜色只表示样式：

| 级别 | 典型动作 | 是否需要确认 | 是否可撤销 |
|---|---|---|---|
| **L0 只读** | 看日志、看会话、复制路径、刷新、筛选/搜索、展开折叠、看门禁/判据 | 不需要，点了立即执行 | 本身不改任何状态，无需撤销 |
| **L1 可逆** | 运行一次、检查回复、检查恢复、保存设置、保存提示词、取消停止、编译论文、只留备注 | 不需要，直接执行 | 能撤：再点一次、改回配置、撤回停止；编译可重跑 |
| **L2 阻断** | 启用、停止、停用（流水线 / 通道）、重置提示词、清空运行记录、提交并批准重启 | 需要，行内二次确认（在这一行里再点一次，不弹窗） | 多半能恢复，但会打断在途工作：停止要等本轮收尾；清空只把台账归档到 `.aris-run/history`；重置后旧模板需自己留档 |
| **L3 破坏** | 强制停止、移除流水线 | 需要，放在详情底部「危险操作」区（默认收起）；移除还要**手打流水线名** | 不可撤销：强制停止可能留下未提交改动；移除只是不再监控，项目文件不动，可重新添加 |

三条使用规则：

- **级别不看颜色**：旧版「绿色=启用、蓝色=主操作、红色=危险」的说法已作废（§3.2.4）
- **二次确认就在原地**：L2 不弹窗，按钮就地变「确认 / 取消」；面板全程不用 `alert` / `confirm`
- **拿不准就往下压一级**：想清空/重置/强制停止之前，先问一句「归档了没、留档了没」

### 3.7 图表怎么读

**阶段树**（总览与流水线详情）

- 父节点 = 11 个阶段，子节点 = 计划项 / 步骤；缩进表示层级，点节点展开收起子层级

- 五个指标切换：**成本（¥）/ 步数 / 耗时（分钟）/ tokens / 上下文占用（%）**
- 一根细柱 = 一轮；轮次多了横向滚动，不压缩柱子宽度

  - 上下文占用逼近 80%/100% 是设计（§2.4），不是故障
  - 连续几轮都在均值线上方 → 看是不是在同一个大块上反复，或该收尾了
- 只显示归档之后的轮次：点过「清空运行记录」以后，台账被移到 `.aris-run/history`，图里就只剩归档后的轮次——不是丢数据

**结论分布（环形图）**

2. 「记录 Y 条」是历史累加，**不是欠账**

## 4. `Aris_Wiki` 面板（读面，全链路只读）

顶部页签：**总览 / 计划 / 产物 / 文档**，默认落在「总览」。右上只有一个「刷新」——流水线选择被收进各页签内部的 chips。

**纯只读**：这个面板能做的事只有刷新、切换页签/chips、搜索、展开收起、打开文件、复制路径。按 §3.6 的分级，它**只有 L0**，页面上不会出现 L1–L3 的按钮。启用、停用、运行一次、停止、编译、收件、裁决、保存设置——全部在 `Aris_Dsh`（§3）。需要跨面板的动作不做假按钮：只给「去 `Aris_Dsh`」的引导，或直接复制路径/摘要让你带走。

**刷新**：默认手动（点「刷新」，或切页签时拉一次）；自动刷新是可选项，默认关，打开后 10 秒一轮。后端连不上时页头明说，并给最后一次成功的时间——不会把旧数据当实时数据静静摆着。

**错误边界**：每个页签各包一层，某一页渲染出错只坏那一页（给重试），不影响其它页签，也不会整面板白屏。

### 4.1 总览

**看什么**：与 `Aris_Dsh` 总览同构——同一套状态词、同一套列、同一套排序，差别只是没有操作按钮。

- **KPI 8 个**：在跑 / 需人工 / 等审核 / 等回件 / 今日轮数 / 今日成本 / 累计 / 阻碍
- **chips**：全部 / 在跑 / 需人工 / 已停止，右侧搜索框
- **一张总表**：状态 / 流水线 / 阶段 / 现在 / 门禁 / 阻碍 / 审核 / 成本 / 下轮；按状态排序（错误 / 需人工 → 运行中 → 等待审核 → 停止）。状态徽标是实底淡色胶囊，配色与 `Aris_Dsh` 同一套 token（`--st-run` / `--st-warn` / `--st-err` / `--st-idle`），深色主题另有覆盖；「下轮」列同样是两行：上行时间（运行中写「本轮结束后」），下行状态（在跑 / 按间隔 / 未排期）
- **点行**：该流水线详情在表格下方展开（内容就是 §4.2 的计划详情）；再点收起
- **窄屏**：横向滚动，表头行吸顶、状态列固定在左侧

各列含义见 §3.1 那张表——两个面板同一口径，看同一份 `state.json` / `runtime.json`。

**能做什么**：只有看、筛、搜、展开（L0）。

### 4.2 计划

**看什么**：一条流水线的全部计划信息（状态条、阶段树、当前阶段、阻碍、门禁、总计划、时间线、最近 8 轮、日志）。页内 chips 直接切流水线，不必回总览。

**状态词与 `Aris_Dsh` 面板同一套**（正在运行 / 停止中 / 等待审核 / 需人工 / 等额度 / 待命 / 已停止 / 出错）。两个面板看到同一件事必须说同一句话，所以 `lib/plan.mjs` 的 `statusOf()` 照抄 `Aris_Dsh` 的判定顺序：出错 → 等额度（GPT 小时额度用尽，会自动恢复）→ 需人工（`state.block` 或 `blocked_on_user`）→ 停止中 → 正在运行 → 已停止 → 等待审核（有在途审稿）→ 待命。判定「等额度」用的是与 `bin/lib/aris-runner.mjs` 同一条规则：带 `attempts 15/15`、`物理送审额度` 的仍算「需人工」，只有纯小时额度用尽才算「等额度」。

**需人工类状态只给一个徽标**：状态列本身是 `需人工` 时，不再叠加第二个 `需人工` 小标签；审稿侧封顶 / 多轮退回也会被 `plan.mjs` 收进 `statusOf()`（读 `bin/lib/review-results.mjs` 的 `humanActions`），所以 wiki 现在也能显示这类「需人工」。

详情页自上而下（分组默认折叠，页头「展开全部 / 收起全部」；单条详情默认展开当前阶段 / 阻碍 / 门禁）：

1. **状态条**：状态、阶段（序号 / 中文名 / id）、现在（本轮起点、已跑时长、步数、上下文）、回件（在途条数、最久已等、是否超阈值）、成本（累计轮数 / 费用 / 今日 / 下轮）
2. **工具条**：展开全部 / 全部收起 + `共 N 阶段（完成 · 进行 · 未开始）`
3. **阶段总表（11 阶段）**：一行一阶段（序号 + id / 阶段名 / 状态 / 计划 a/b · 已执行 · 待做 / 进入 / 退出），点行在该行下方展开这一阶段的明细；进入 / 退出列超 46 字截断，悬浮看全文
4. **当前阶段**：默认展开的那一段，体内分组见第 6 条。总表「审核」列显示 `上轮 · <verdict> · MUST n / SHOULD m`（取自 `reviewBriefs()`）
5. **阻碍**：见下方规则表；每条带严重度、类型（`state-block` / `blocked-on-user` / `stopping` / `gate` / `blocked-until` / `error` / `review-pending` / `gate-pending` / `budget` / `never-run`）、说明、证据，`需人工` 标出必须人裁决的
6. **门禁**：id、状态（已裁/待做）、裁决词、判据、实测值
7. **总计划（与阶段总表同一张表）**：2026-11-19 起不再额外画一棵重复的阶段树，直接复用上面那张 11 阶段表；点行展开后按五组显示，**每组单独可折叠**：
   - 进入 / 退出条件（`pipeline/PIPELINE.md`）
   - 计划项（PIPELINE.md 的 `- [ ]` 条目，全量不截断）：`☑/◐/☐` + 右侧「N 步」表示对应几个状态机步骤
   - 待做（自己能干）：`阶段序号.步序` + 状态机 id 徽标 + 摘要
   - 等外部回件：送审 / 待回复类步骤单列，避免和可自干项混排
   - 已完成步骤：同上；若同一步骤编号也出现在 `todo` 里，标「仍挂在待做」，只显示一次
8. **进展时间线**：轮次 / 审查回件 / 门禁裁决三类事件按时间倒序
9. **最近 8 轮执行**表：轮次、开始、步数、成本、结果（含 exit）
10. **日志抽屉**：阻碍里点「看日志 / 看样子」就在页内弹出 `.aris-run/runs/<runId>/final.txt`（轮次摘要）或 `stderr.log` / `runtime.json`，不用离开面板

**计划项与步骤怎么对应**：不按序号硬配（PIPELINE.md 的条目顺序与状态机步骤号并不一一对应，实测 S4b 第 1 条是 GMM 策略、第 3 条才是 `S4b.1a` 做的判据掩码预编译）。用最长公共子串 ≥5 个连续字符匹配，一条步骤只认一个计划项；对不上就显示「未开工」，不做假勾选。

**阻碍动作按钮**：`看日志 / 看样子 / 看门禁 / 看判据 / 看是哪一步` 直接可用（页内滚动或弹抽屉）；`打开邮箱队列 / 看预算` 要跨到 `Aris_Dsh` 面板，没有公开跳转 API，降级为**复制路径 + 提示去 `Aris_Dsh` 操作**，不做点了没反应的假按钮。

阻碍规则表（`lib/plan.mjs` 的 `blockersOf()`，按严重度排序）：

| 类型 | 何时出现 | 算需人工 | 动作 |
| --- | --- | --- | --- |
| `state-block` | `state.block` 有内容，且之后没有成功轮次 | 是 | 看是哪一步 |
| `blocked-on-user` | `state.status` 或任一阶段 = `blocked_on_user` | 是 | 看是哪一步 |
| `gate` | `runtime.gateReason` 非空且流水线没在跑 | 是 | 看门禁 |
| `error` | `runtime.lastError` 或连续错误 ≥2 | 否 | 看日志 |
| `stopping` | 已登记停止、本轮收尾后不再起轮 | 否 | — |
| `blocked-until` | `runtime.blockedUntil` 还在未来（预检退避） | 否 | 看样子 |
| `review-pending` | 邮箱 `projects.json` 登记、且 `in/<base>.request.md` 仍在的在途请求 | 否 | 打开邮箱队列（复制路径） |
| `gate-pending` | 门禁 `status=pending` | 否 | 看判据 |
| `budget` | 最近一轮上下文 ≥80% | 否 | 看预算（复制路径） |
| `never-run` | 从没跑过 | 否 | — |

在途审稿的判据与 dsh 流水线同源（`bin/lib/aris-runner.mjs` 的 `pendingReviews`）：邮箱索引 + 在途请求文件双条件，超时阈值 = `max(30, 2×Kimi 取件周期)` 分钟（当前 Kimi 周期 15 分钟 → 30 分钟）。超阈值**只标「已超阈值，Kimi 可能没取件」**，不转人工——这条以前看 `.aris/reviews/*.json` 的 mtime，而那是只增不删的归档目录，导致流水线明明在跑却长期报「需人工」。

**能做什么**：看、展开、点阻碍里的只读动作、复制路径（L0）。

### 4.3 产物

**看什么**：按流水线分开的产物——主论文卡、六组文件表、右侧预览。

**能做什么**：切 chips、点行看预览、调宽、打开原文件 / 复制路径（全部 L0）。编译与写操作在 `Aris_Dsh`。

- 顶部 chips 选流水线（**产物按流水线分开**）
- 主论文卡：`主论文 · 中文稿`、文件名、体积、生成时间、「打开 PDF」「看源码」
- **文件表 + 预览**：左侧文件表按六组列（论文 `.tex/.md`、图、实验（`dataset_gen/out`、`pipeline/out`、`runs`）、审查、运行、幻灯片）；左表与预览撑满页签高度、表格自身滚动、表头吸顶；点一行右侧出预览，中间拖拽条可调宽、双击复位、宽度记忆
- 预览：文本按 Markdown 渲染、图片直显、PDF 用 iframe 内嵌（高度 `min(72vh, 680px)`，超上限的 PDF 只给「打开原文件」）；读不了的给占位，用「打开原文件」「复制路径」带走
- 窄屏退成单列，预览移到表格**上方**
- 只读：编译与写操作在 `Aris_Dsh`

产物扫描上限：单组 400 文件、总 1500、文本 2MB、二进制 4MB、深度 4；越界路径直接 404。

### 4.4 文档

知识库索引：ARIS 上游文档（`references/docs`）、`MCP_REPLACEMENTS.md`、各项目 `literature/` `notes/` `search_logs/`。一级按流水线分组、二级按文件类型（chips）、支持搜索与阅读器（60 秒缓存，最多 2000 条）。纯读，点开就是阅读器，没有编辑入口。

**看什么**：按流水线分组的知识库索引与阅读器正文。**能做什么**：搜索、切 chips、点开文件阅读（L0）。

## 6. 审查闭环（Kimi 3.1 Pro / GPT 两条通道）

`via` 决定走哪条：`kimi-mailbox`（人工/Kimi 客户端取件）、`codex`（本机 ChatGPT 直跑）、`direct`（OpenAI 兼容端点）。

```
子进程写请求 → .aris/mailbox/in/<ts>-slot1.request.md
        ↓（Kimi 桌面客户端定时取件，人工/自动作答）
回复落 aris-mailbox/out/<ts>-slot1.reply.md
        ↓（面板「检查回复」或每轮启动时的 collect-all）
.aris/reviews/<ts>-slot1.json    ← 记 verdict、score、identity=reviewer-declared:<模型>
        ↓（本轮收尾或下一轮）回写 state：把 MUST/SHOULD 转成下一块的 todo
```

GPT 通道（`via: codex`）的数据流：

```
派单（面板 / CLI --via codex）
   ↓ 提示词 = role + output 两段模板渲染（面板可改可预览）
送审材料（文件清单或任务正文）→ 拼成 .aris-run/codex/<ts>-<task>.task.md
   ↓ codex exec --json -C <工作区> -m <模型> -c model_reasoning_effort=<强度>
事件流 → .aris-run/codex/<ts>-<task>.events.jsonl（thread.started / item / usage）
   ↓ 同时留一条真会话：~/.codex/sessions/…/rollout-<ISO>-<thread_id>.jsonl
回复 → <项目>/.aris/reviews/<ts>-codex-<task>.md，记 model / cliModel / tokens / sessionId
   ↓ 面板「复制续聊命令」→ codex resume <sessionId>
```

要点：
- **身份靠自报**：回复首行 `Reviewer-Model:` 决定 `identity`；缺失即视为未验证
- **同族审查只能算 provisional**：执行是 DeepSeek，审稿必须跨族（Kimi/Claude/GPT）才算真对抗
- **面板不伪造结论**：所有裁决只从 `.aris/reviews/*.json` 与 `state.json` 读，不接受手填
- 额度：订阅制，不进 `costs.jsonl`；比 API 更容易撞 5 小时窗/周上限
- **单飞**：两条通道共用 `.dsh/.review.lock`，同一时刻只跑一条（详见 §3.4.6）
- **续聊是另一条路**：`codex resume` 不受面板闸门与审计约束，只受订阅额度约束；要审稿还是走派单
- **面板改了线路、流水线却还送 Kimi**：先看线路卡下方项目的 `active` 是否跟上；没跟上就再点一次线路按钮保存（会同步 `reviewer.json`）。仍然不对，查 `pipeline/review/mailbox_bridge.py` 读到的 `external.review.channel` 与项目 `active` 是否一致
- **GPT 送审失败后邮箱没有请求**：这是设计如此——GPT 通道失败直接退出、不降级，修好额度/线路后重跑同一命令即可
- **调度器（`aris-runner.mjs`）特别说明**：2026-11-19 起它的 import 版本串跟随插件重载（`ARIS_LIB_REV`，由 `plugins/dsh-aris/index.js` 在每次 `lib()` 时写入），不再需要手动升 `?v=N`；其它 `lib/*.mjs` 仍要升版本号。
- **改完调度器代码后**：`plugin_manager set_plugin include:aris` 关→开即可生效，不必重启 DSH；若快照的 `runnerRev` 没变，说明重载没走到。
- **`state.json` 超过 400 KB 时**：`readText()` 默认截断 400,000 B，截断后 JSON 解析失败曾被当成「没有状态」，导致 `preflight()` 放行、每 60 秒空起一轮（2026-11-20 实测 6 分钟 6 轮、约 ¥0.49）。`preflight()` 现已改用 `readJsonFull()` 整份读，解析失败按「状态不可判定」停跑 5 分钟；`done` 只增不删是根因，定期归档可缓解。
- **改了 `bin/lib/*.mjs` 面板行为没变**：插件宿主按 URL 缓存模块，`lib` 之间互相 `import` 也要带版本号（如 `from './review-route.mjs?v=3'`），改完必须升版本再 `plugin_manager set_plugin include:aris` 关掉再开；只重启插件不升版本会继续跑旧代码（踩过：`readProjectSlots is not defined`）
- **线路卡上的项目标签是琥珀色**：说明该项目 `reviewer.json` 的 `active` 还没跟上面板；点一次线路按钮即可同步（保存会逐个项目写入并回读）

**GPT 通道（via=codex）**不必等外部取件，一轮内同步跑完：

```
prompts → codex.exe exec（stdin 喂提示词，-o 落 stdout 文件）
        ↓  超时 kill、审核锁（与 Kimi 共用）、每小时限额、tokens 记账
.aris-run/codex/<stamp>-<任务分类>.task.md   ← 送进去的原文
        ↓
.aris/reviews/<时间>-slot<N>.md          ← 审稿正文，首行 model/effort 以 CLI 头部为准
.dsh/codex-runs.jsonl                    ← 每次调用的 model/effort/tokens/耗时/成败
```

- 配置在 `bin/aris-review.mjs --via codex`，任务分类用 `--task` 选（决定模型与强度，默认 `routine_review`，旧参数 `--gate` 作别名），`--model/--effort` 只对这一次生效
- **两条通道互斥**：`acquireReviewLock`（`bin/lib/review-lock.mjs`）保证 Kimi 与 GPT 不会同时审同一份稿；锁 TTL：Kimi 6 小时、GPT 单次超时 + 1 分钟
- 复现旧结论用「按原配置重跑」，读 `codex-runs.jsonl` 里那次的 model/effort；**复现不要揉进日常迭代**，否则失去可比性
- 不加 Windows 计划任务：只由 DSH 运行期（一轮开始时、或面板手动派单）触发

## 7. 常用剧本

**启动一条流水线**
`Aris_Dsh → 流水线 → 点该行 → 启用`（或「运行一次」马上跑一轮）→ 总表与详情状态变「正在运行」→ 用「会话」旁观。

**暂停而不留半截**
点「停止」（L2，行内二次确认；等本轮跑完），不要「强制停止」（L3）。收尾后状态变「已停止」。

**本轮卡在等人**
`Aris_Wiki` 总览的总表里看到「需人工」→ 点行在表下方展开，或到「计划」页展开「阻碍」：红条那条就是卡住的原因（`state-block` / `blocked-on-user` / 门禁未过），点「看是哪一步 / 看门禁」直接定位 → 去 `Aris_Dsh → 流水线 → 该条详情 → 需要人工介入`：要写回 state 并放行下一轮用「提交并批准重启」，只留说明用「只留备注」；额度封顶就填追加次数再批准。
注意：**在途等审稿不算「需人工」**，它显示为「等待审核」，超阈值只在阻碍里提示「已超阈值，Kimi 可能没取件」。

**审稿一直不回来**
总表「审核」列有在途条数，详情状态条的「回件」写着最久已等多久、是否超阈值（阈值 = max(30, 2×Kimi 取件周期)）→ 确认 Kimi 应用是否开着、定时任务是否启用 → 或手动把 `out/` 的回复放进邮箱后点「检查回复」。

**只想看进度**
只开 `Aris_Wiki`：总览看 KPI 与总表，点行（或切到「计划」页）看阶段树、总计划、步骤、阻碍、时间线。

**编译论文**
`Aris_Dsh → 产物 → 编译论文`；CN 稿走 xelatex 23 页，EN 稿当前因 32 行中文占位（`【TODO-EN】`）编不过，报 `Unicode character 【 (U+3010)` —— 这是**内容缺口**，不是工具问题。

**新增一条流水线**
`node bin/aris-run.mjs add --root <项目> --driver auto`，面板会自己出现；也可以在「流水线」页直接填根目录添加。

| 面板「查看会话」说找不到 rollout | 会话被清理，或 id 抄错/截断 | 用完整 UUID；`~/.codex/sessions` 只报体积不自动删 |
| 事件流里 `thread.started` 有但没回复 | 进程超时被 kill | 调高「单次超时」或减小送审体积；看 `.events.jsonl` 末条 |

| 在设置页打字时输入框被清空/回退 | 旧版 10 秒轮询返回后会整体覆盖表单值 | 已修：轮询不再覆盖正在编辑的字段；保存后按磁盘重读回显 |
| `Aris_Wiki` 某个页签白屏，或点页签没反应 | 旧版没有错误边界，单个组件抛错会拖垮整个面板 | 已修：每个页签独立错误边界，只坏那一页并可重试 |

## 10. 边界与安全

- **只读 vs 写**：`Aris_Wiki` 全链路只读（没有任何写路径）；写操作只发生在 `Aris_Dsh`（启停、门禁、编译、设置、收件），且写面内部再按 L0–L3 分级（§3.6）
- **不伪造**：面板从不生成裁决，只展示 `state.json` / `reviews/*.json` 的既有记录
- **同步盘**：项目与邮箱在 `SynologyDrive` 上，写它需要提权；`.aris` 状态目录可用 `--state-dir` 留在本地工作区
- **会话**：只读查看器不会写入会话文件；运行中的会话**不要在里面发消息**，会和 headless 抢写
- **删除**：一律走 `node bin/recycle.mjs`，回收站或 `archive/trash/`，不做永久删除

## 11. 术语表

| 词 | 含义 |
|---|---|
| 轮 / wake / round | 一次子进程执行（几十分钟、几十步） |
| 步 / step | 一轮里的一个模型回合（含工具调用） |
| 原子块 | 一轮只做一件可验证的小事，不做半成品 |
| 门禁 / gate | 阶段之间的硬检查点，需人裁决或自动判据通过 |
| 阻碍 / blocker | 当前进退两难的原因（等回件、需人工、门禁未裁、错误）；分严重度 `error/warn/info` |
| 需人工 | 只有 `state.block`、`blocked_on_user`、门禁未过才算；流水线在跑但等审稿回件**不算** |
| 等回件 / 在途审稿 | 邮箱里已发、回来的 `in/<base>.request.md` 还在的请求数；超阈值（max(30, 2×Kimi 周期)）只告警 |
| 租约 / lease | `gate.py` 的 A/B 互斥锁，防止两个执行者同时改状态 |
| 交接 / handoff | `handoff.mode`：由 DSH 起轮还是由 Kimi 起轮 |
| 槽位 / slot | 审稿通道编号；`tier` 是审查深度档（L1/L2） |
| 预算 / budget | 单轮调用数与上下文上限，触顶强制收尾 |
| 总表 | 总览页那张「一行一条流水线」的汇总表；点行在表下方展开详情 |
| 操作分级 L0–L3 | 只读 / 可逆 / 阻断 / 破坏四档，决定要不要二次确认、能否撤回（§3.6） |
| 阶段树 | 父节点=阶段、子节点=计划项/步骤的层级视图，状态点表示完成/进行/待做（§3.7） |
| 外推轮次 | 图表里超出实际记录的轮次，按已有轮次推算，仅示意趋势（§3.7） |
